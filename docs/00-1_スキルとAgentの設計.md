# 00-1 スキルとAgentの設計（進め方自体の要件定義・設計）

状態： v0.1 叩き台（2026-11-26）。本人の確認で確定する。
位置づけ： RAG本体の要件定義（01）の前に置く「工程0」。RAGをどう作るかではなく、
RAGを全工程で作るための仕組み（スキルとAgent）をどう設計するかを決める文書。

---

## 1. なぜこの設計が要るか

- スキルとAgentを場当たりに作ると、工程ごとに書式も粒度もバラバラになり、
  「標準化した」と言えなくなる。作る前に型を決める
- 型が決まっていれば、別のAgent（別のモデル、別の実行環境）が途中から
  参加しても同じ進め方を再現できる。それが標準化の証拠になる
- ポートフォリオとしても、この文書自体が「手順を標準化する前に、
  標準の設計から入る人」という証拠になる

## 2. 進め方自体への要件（PR： Process Requirements）

| 要件 | 内容 | 判定方法 |
|---|---|---|
| 再現性 | スキルだけを読んだAgentが、口頭の追加指示なしに、その工程の成果物を同じ形式で出せる | 未知のAgentにスキルだけ渡すドライランで確認（評価方法の節） |
| ゲートの客観性 | 各工程の完了条件が、実施した本人以外でも合否を判定できる文で書かれている | ゲート文に主観語（「十分に」「適切に」等だけ）がないかレビュー |
| トレーサビリティ | 要件の名前→設計→製造→テストの対応が、文書をたどって追える | 対応表が外部設計以降の各成果物に付く |
| 承認点の明示 | 人（本人）が判断する点が、工程ごとに明示されている。Agentは承認を代行しない | Agent定義に「承認点」の節がある |
| 生成と検証の分離 | 成果物を作った目と、次工程で検証する目を分ける | 工程Agentが分かれている／検証観点がスキル側にある |
| 差し戻し可能 | 後工程で前工程の問題を見つけたら、前工程の成果物を更新して記録を残す進め方が定義されている | 共通スキル「差し戻し」の手順に従う |
| 公開／私用の分離 | 実データと秘密情報を公開物に入れない確認が、全工程のゲートに含まれる | 共通スキル「公開前チェック」をゲートで参照 |
| 改善の仕組み | 工程の終わりに振り返りを行い、手順の不足はスキル／Agent定義の改版として残る | 改版履歴がgitに残る／振り返り記録が成果物に付く |
| 持ち出し可能性 | スキルとAgentが特定の製品に縛られず、Muse系とCopilot系の双方へ移せる中立形式である | §7の対応表で変換先が示されている |
| 最小性 | スキルとAgentの数が目的に対して過剰でない。1工程に中核スキル1件＋共通スキルの参照が原則 | 構成レビュー（§4.4、§5.4） |

対象外（この設計では決めない）：
- RAG本体の技術選定（埋め込みモデル、ベクトルDB等）→ 内部設計工程で決める
- 実行環境の自動化（CI、自動オーケストレーション基盤）→ v1では人間＋進行管理Agentの手動連携で回し、自動化はST後の改善とする

## 3. 全体構成

```text
本人（承認者・最終判定）
   │ 承認・差し戻し
進行管理Agent（orchestrator）
   │ 工程開始の指示、ゲート確認、状態管理（00_工程定義.md）
   ├─ 要件定義Agent ── スキル: requirements ＋ 共通スキル
   ├─ 外部設計Agent ── スキル: external-design ＋ 共通スキル
   ├─ 内部設計Agent ── スキル: internal-design ＋ 共通スキル
   ├─ 製造Agent     ── スキル: implementation ＋ 共通スキル
   ├─ UT Agent      ── スキル: unit-test ＋ 共通スキル
   ├─ IT1 Agent     ── スキル: integration-test-1 ＋ 共通スキル
   ├─ IT2 Agent     ── スキル: integration-test-2 ＋ 共通スキル
   ├─ IT3 Agent     ── スキル: integration-test-3 ＋ 共通スキル
   └─ ST Agent      ── スキル: system-test ＋ 共通スキル
   各Agentの成果物 → 次工程の入力（引き継ぎ形式は§6で統一）
```

原則：
- スキル＝手順の正本（状態を持たない、再利用できる）
- Agent＝役割と責任範囲（スキルを使って成果物を出す、承認点で止まる）
- 進行管理Agentは実作業をしない。状態とゲートだけを見る

## 4. スキル設計

### 4.1 ファイル形式
- 置き場所： `skills/<番号>-<slug>/SKILL.md` ＋ `skill.yaml`
- SKILL.mdにフロントマターを混ぜず、メタデータはskill.yamlに分離する
  （ネロのカスタムスキルで運用実績のある形式に合わせる）
- 言語： 日本語を正とする（対象読者が日本の開発現場と本人自身のため。
  slugとIDは英語）

### 4.2 SKILL.md の必須章（全スキル共通の型）
1. 目的（1〜3行、その工程で何を決める／作るか）
2. 入力（前工程の成果物名で書く）
3. 成果物（ファイル名まで具体的に）
4. 手順（番号付き、動詞から始める、1項目1判断）
5. ゲート／完了条件（あとから誰でも合否を判定できる文で）
6. 失敗しやすい点（過去の実例ベースで書く、一般論で埋めない）
7. 次工程への引き継ぎ（§6の形式を指定）

### 4.3 書き方の規則
- 手順は「すること」だけを書く。背景説明は目的の節に寄せる
- 道具・コマンド・パスは正確な名前で書く
- 個人情報、実データの中身、秘密情報はスキルに書かない（スキルは方法だけ）
- 判断が割れる点は手順に埋めず「未決事項として挙げる」と書く

### 4.4 粒度
- 1工程＝中核スキル1件。工程をまたぐ手順は共通スキルに切り出す（§4.5）
- スキルが長大になったら references へ分割する。逆に、1回しか使わない
  手順はスキル化せず、その工程の成果物にメモとして残す

### 4.5 共通スキル（設計のみ。作成は要件定義工程の後で判断）
| slug | 目的 | 使う工程 |
|---|---|---|
| common-traceability | 要件の名前との対応表の作り方と確認手順 | 外部設計〜ST |
| common-self-review | 成果物をゲート前に別の目で確認する手順（レビュー観点の資産化の型）【2026-11-26に本人の指示で作成済み】 | 全工程 |
| common-handover | 引き継ぎメモの形式と、差し戻しの記録方法 | 全工程 |
| common-privacy-check | 公開リポジトリへの実データ・秘密情報の混入チェック | 製造、IT3、ST |
| common-retrospective | 工程末の振り返り（構想・評価基準と実態のずれを見る）と、スキル改版へのつなぎ方 | 全工程の末尾 |

## 5. Agent設計

### 5.1 ファイル形式
- 置き場所： `agents/<番号>-<slug>.agent.md`、進行管理は `00-orchestrator.agent.md`
- 製品固有のフロントマターは付けない中立形式（§7）

### 5.2 Agent定義の必須章
1. 使命（1〜2行、その工程で何に責任を持つか）
2. 担当工程
3. 入力／成果物（スキルと一致させる）
4. 使うスキル（中核スキル＋参照する共通スキル）
5. 承認点（どこで止まって人の判断を仰ぐか）
6. 禁止事項（推測で埋めない、実データを公開物に入れない、前工程の
   成果物を無断で前提から変えない、等。その工程固有の禁止も足す）
7. エスカレーション（判断できないときに、誰へ・何を添えて上げるか）
8. 完了報告の形式（成果物の場所、ゲート自己確認の結果、未決事項）

### 5.3 責任分界
- 1工程1Agent。前の工程の判断を、後ろのAgentが勝手に覆さない
  （覆す場合は差し戻しとして記録する）
- 進行管理Agentは成果物を作らない。ゲート未達を「完了」と報告しない
- STの受け入れ判定はAgentの仕事ではない（材料を揃えるまで）

### 5.4 粒度
- 工程と同数＋進行管理1件が上限の目安。これ以上増やすときは、
  責任が本当に分かれるかを確認してからにする

## 6. 連携プロトコル（引き継ぎと状態管理）

- 引き継ぎは口頭で完結させない。次工程の入力になる成果物ファイルと、
  次の3点を成果物末尾か引き継ぎメモに残す：
  (1) ゲート自己確認の結果 (2) 未決事項 (3) 差し戻し事項
- 工程の状態（未着手／実施中／ゲート待ち／完了）は
  `docs/00_工程定義.md` の状態表だけが正本。更新は進行管理Agentの役目
- 承認の記録は、承認した日と承認者が分かる形で状態表か成果物に残す

## 7. 実行環境との対応

| 本設計の中立形式 | Muse / Muse Skills | GitHub Copilot |
|---|---|---|
| skills/<slug>/SKILL.md | そのままスキルとして読める | Agent Skills（.github/skills/）へ配置換えで使える |
| skills/<slug>/skill.yaml | 実行環境側のメタデータへ読み替え | SKILL.md冒頭のフロントマターへ変換 |
| agents/*.agent.md | サブエージェント定義の素材（役割文として） | custom agents（.github/agents/）へ変換 |
| 進行管理Agent | メインエージェントが兼任可 | 人＋チャットの司令塔が兼任可 |

- v1の実行はネロ（Muse）上で、進行管理＝ネロ本体、工程Agent＝
  工程ごとのサブエージェント／作業単位として回す想定
- Copilotへの持ち出しは変換対応表までを用意し、実変換はST後の
  改善項目とする（やったと言わない）

## 8. スキル／Agent自体の評価方法

- ドライラン： 要件定義スキルだけを、事情を知らないサブエージェントに
  渡し、叩き台（01 v0.1）と同等の構成の成果物が出るかを見る。
  出なければスキルの不足として改版する（再現性の確認）
- 実運用フィードバック： 各工程の振り返りで「スキルに書いてなかった
  判断」を数え、多い工程のスキルから改版する
- 評価結果はこの文書の改版履歴として残す
