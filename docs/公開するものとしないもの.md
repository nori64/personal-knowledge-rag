# 公開するものとしないもの（GitHubポートフォリオの範囲）

「ローカルで構築するなら、GitHubには何が残るのか」への答えを先に決めておく文書。
原則は1つ： **実データそのもの以外は、全部公開する。**

## GitHubに残るもの（ポートフォリオ本体）

| 残るもの | 中身 |
|---|---|
| コード一式 | 取り込み・検索・評価のコマンドラインツール、MCPサーバー、テストコード。誰でもcloneして動かせる |
| 設計文書一式 | 工程定義、スキルとAgentの設計、要件定義書、外部設計書、内部設計書、各テスト仕様書 |
| スキルとAgentの定義 | 全工程分の標準手順と役割定義（このプロジェクトの進め方そのもの） |
| 過程の記録 | 決定の記録、工程記録、振り返り（process/ 配下） |
| 架空サンプルの文書セット | 運用知識を模した架空の文書（実物の構造だけ真似て、内容は創作）。読み手がそのまま取り込んで試せる |
| サンプルでの評価一式 | サンプル文書に対する質問セット（期待する出典つき）と、評価の実行結果。読み手が同じ手順で再実行して、同じ数字を再現できる |
| 実データでの評価の「数字だけ」 | 実物の運用知識で測った集計値（質問の件数、Recall@5、出典の正確率、答えなし質問への正しさ、方式どうしの比較表）。質問文と文書の中身は出さない |
| README | 課題、構成、使い方、評価結果の要約、既知の限界 |

つまり読み手は、clone → サンプル取り込み → 検索 → 評価の再実行まで全部たどれ、
そのうえで「実データでもこの数字だった」という集計結果まで確認できる。

## GitHubに残らないもの

| 残らないもの | 理由 |
|---|---|
| 実物の運用知識の文書 | 個人の文脈を含むため。ネロの作業環境の中だけに置く |
| 実データから作ったベクトルDB（索引） | 文書の内容を復元しうるため、実物と同じ扱いにする |
| 実データ用の質問セットの文面 | 運用の内情が文面から読み取れるため。件数と集計値だけを公開する |
| 認証情報・個人情報 | 論外として、公開前チェックの対象にする |

## サンプル文書の作り方（外部設計・製造で守ること）

- 実物の「種類と構造」を真似る： 運用ルールの文書、スキルの手順書、台帳のような表、等
- 件数は評価が意味を持つ規模にする（十数件以上を目安に外部設計で決める）
- 内容はすべて創作し、実在の人名・数値・ルールを転用しない
- サンプルであることをフォルダ名とREADMEで明示する

## 判定方法

- 公開前のチェック（共通スキルの「公開前チェック」）で、上の「残らないもの」が
  混ざっていないことをファイル単位で確認してから公開する
