## 1. モジュール構成

実装は Python。置き場所は `src/ragcli/`。

| モジュール | 責務 | 入力 → 出力 |
|---|---|---|
| config | 設定ファイル（ragcli.toml／ragcli.local.toml）の読み込みと検証 | 設定ファイル → 設定オブジェクト（文書フォルダ群、索引の置き場所、質問セットの場所） |
| parser | 文書ファイルをテキストと見出し構造に変換する | ファイル → 見出しつき段落の列 |
| chunker | 見出し単位を基本に、長さ上限で分割し、出典情報を付ける | 段落の列 → チャンクの列（文書名、見出し、本文、位置） |
| embedder | テキストをベクトルに変える。実装は差し替え可能にする | テキスト → ベクトル |
| keyword | キーワード索引の構築と検索（BM25） | チャンク群 → 索引／質問 → 順位つき結果 |
| vectorstore | ベクトルとチャンク情報の保存・読み込みと、類似度検索 | チャンクとベクトル → 索引ファイル群／質問ベクトル → 順位つき結果 |
| search | キーワードとベクトルの結果統合、候補あり判定、結果JSONの組み立て | 質問 → 外部設計の検索結果JSON |
| eval | 質問セットの一括実行と集計 | 質問セット → 質問ごとの結果と集計 |
| cli | コマンドラインの入口。引数解釈と終了コードへの変換、本人が直接使う簡易表示の整形も担う | コマンド → 各処理の呼び出し |
| mcp_server | MCPツール `search_knowledge` の提供（第2段階） | MCPの呼び出し → search の結果 |

依存の向き：cli と mcp_server は search／取り込み処理を呼ぶ側で、呼ばない側（parser、chunker、embedder、keyword、vectorstore）は cli を知らない。単体テストで差し替えられる境界は embedder（モック化）と、search の中の統合処理（純粋な計算として切り出す）。

製造範囲の区切り：初版の製造は mcp_server を除く範囲（コマンドラインまで）とする。MCPサーバーは、結合テストの外部結合の前に製造する。

## 2. チャンクの切り方

- Markdownは見出し（#〜###）で区切り、見出し配下の本文を1単位の基本とする
- 1単位が長い場合は段落単位で分け、上限は初期値として 800 文字、重なりは 80 文字（初期値。総合結合の評価で調整する）
- 表は行の途中で切らない。表が上限を超える場合は表のまとまりを優先して上限を超えることを許す
- テキストファイルは空行区切りを段落として扱う。PDFはページ単位でテキスト化してから段落扱いにする（初版の保証範囲外だが、取り込み経路は共通にする）。PDFの変換には pypdf を第一候補とし、製造の最初に動作を確認して確定する
- チャンクには文書名、見出し（無い場合は文書名）、文書内の位置（先頭からのチャンク通し番号）を持たせる

## 3. 埋め込みモデル

### 3.1 決め方（選定手順）
決め打ちしない。次の手順で、サンプル質問セットの実測で決める。

1. 候補をすべて同じ質問セット（サンプル30件以上）で実行し、ベクトルのみの Recall@5 と取り込み時間を測る
2. 一番良い候補を採用する。同程度なら、軽くて速い方を採る
3. 結果は評価結果の文書に、候補ごとの数字つきで残す

### 3.2 候補（すべてローカル実行）
- multilingual-e5-small（軽い。過去に別用途の意味検索で期待に届かなかった経験があるため、そのまま本命にしない）
- multilingual-e5-base
- bge-m3（重いが多言語に強いとされる。実行環境で実用的な時間に収まるかも含めて測る）

外部APIの埋め込みは候補に入れない。入れる場合は外部設計の制約どおり、送信範囲と理由を明記して本人の確認を取ってからにする。

### 3.3 実装
- 実装は sentence-transformers を使う。モデル名は設定ファイルで切り替えられるようにし、索引にはモデル名を記録する（モデルを変えたら再取り込みが必要と判定できるようにする）

## 4. キーワード検索

- 方式は BM25。日本語の分かち書きは Janome（形態素解析）を使う。Janomeが使えない環境では文字の2グラムに切り替える（切り替えは自動ではなく設定で明示する）
- 数字と英字の並び（型番、日付など）は形態素で割れやすいので、分かち書き後の語に加えて、元の文字列の部分一致も補助として使うかは、総合結合の評価で比べる（初版は形態素のみで始める）
- キーワード索引はファイルに保存しない。検索と評価の開始時に、チャンク情報から組み立てる（対象規模では十分に速く、索引の版管理がベクトル側の1か所で済む）
- 分かち書きで使う品詞の範囲は製造で決め、総合結合の評価で比べる対象に含める

## 5. ベクトル索引

- 初版は専用DBを使わず、ベクトルの行列（numpy形式）とチャンク情報（JSONL）をファイルで持ち、検索は総当たりのコサイン類似度とする
- 理由：対象規模（文書数百件、チャンク数千件程度）では総当たりで十分に速く、依存が少なく、動きが追いやすい。規模が育って遅くなったら、vectorstore モジュールの境界で専用DBへ差し替える
- 索引フォルダの中身：ベクトル行列、チャンク情報、取り込み記録（次の節）

## 6. 差分取り込みと索引の版管理

- 取り込み記録（manifest）に、ファイルごとの内容ハッシュ（SHA-256）、取り込み日時、埋め込みモデル名、索引の形式の版を記録する
- 再取り込み時はハッシュを比べて、変わったファイルだけを再分割・再埋め込みする。消えたファイルのチャンクは索引から除く
- モデル名か形式の版が記録と合わない索引は、外部設計どおり「版が合わない」として扱い、再取り込みを促す

## 7. 結果の統合と、候補あり判定

- 統合は順位の統合（Reciprocal Rank Fusion）とする。キーワードとベクトルでスコアの尺度が違うため、生スコアの単純な合算はしない。統合の定数は一般的な初期値（60）から始める
- 外部に出すスコアは、統合結果を0〜1に正規化した値とする（外部設計の定義どおり）。正規化は、返した結果の中の最大・最小に合わせる方式にしない（最上位が常に関連度1.0になり、閾値判定が壊れるため）。「両方の検索で1位だった場合の理論上の最大値」で割る方式とし、絶対値に意味を残す
- 候補あり判定：最上位の正規化スコアが閾値以上のとき「候補あり」とする。閾値の初期値は、サンプル評価で「答えがある質問」と「答えがない質問」のスコア分布を見て決める（決め方をここに固定し、値そのものは総合結合で確定して評価結果に残す）

## 8. 評価の集計

- 方式は `--method` で切り替える：キーワードのみ／ベクトルのみ／組み合わせ（統合）
- Recall@5：期待する文書名と見出しが上位5件に入った質問の割合
- 出典の正確率：返した結果の出典（文書名・見出し）が実在する割合（実装上は常に実在するはずで、崩れたら不具合として扱う）
- 答えなし検出率：答えがない質問のうち「候補なし」と返せた割合。逆に誤って「候補あり」になった割合も併記する
- 出力は質問ごとの結果と集計をJSONと表の両方で出す

## 9. 例外処理（モジュールごと）

| 場面 | 扱い |
|---|---|
| 設定ファイルが読めない・項目不足 | config が理由を明示して失敗を返す。cli は終了コード2に変換する |
| ファイルが読めない・形式が想定外 | parser はそのファイルを警告として返し、取り込み全体は続ける |
| 埋め込みの実行失敗（モデル取得失敗など） | 取り込み全体を止め、理由を表示する（中途半端な索引を残さない。作業用ファイルは破棄する）。cli は取り込みの実行失敗として終了コード4に変換する |
| 索引が無い・版が合わない | search／eval は終了コード3に変換する |
| 質問セットの行の形式が違う | eval は行番号と理由を出して終了コード4に変換する |

## 10. MCPサーバー（第2段階）

- 実装は Python の MCP 公式SDKを使い、通信は標準入出力とする
- ツール `search_knowledge` は search モジュールの処理をそのまま呼び、同じJSONを返す。MCP側に検索ロジックを持たない

## 11. 単体テストで確認する観点（単体テスト工程への引き継ぎ）

- chunker：見出しで割れること、長さ上限と重なり、表が途中で切れないこと、見出しなし文書の扱い
- search の統合処理：順位の統合が手計算と一致すること、正規化が0〜1に収まること、候補あり判定の境界
- eval の集計：Recall@5 などの計算が小さな手作りデータで手計算と一致すること
- config と差分判定：ハッシュが同じなら再取り込みしないこと、消えたファイルが除かれること
- embedder はモックに差し替えて、上記がモデルなしで動くこと

## 12. 差別化の検討（自己レビューの検出率の測り方）

差別化ポイントの「検討中」にある、自己レビューの検出率の実測は、次の形で設計しておく（実施はシステムテストの後か、内部設計以降の余力で判断する）。

- 過去の設計文書のコピーに、種類の違う欠陥を決めた数だけ埋め込む（対応づけの漏れ、前提の食い違い、未定義の例外、数値の不整合など）
- 埋め込んだ場所を知らないAgentに、共通スキル「自己レビュー」でレビューさせ、拾えた数と種類を数える
- 結果は「検出率」として過程の記録に残す。拾えなかった種類は、観点の不足としてスキルへ1行足す

- ディレクトリ構成は本書のモジュール表どおりとする

## 14. 設定項目の一覧

| 項目 | 内容 | 決める場所 |
|---|---|---|
| 文書フォルダ（複数可） | 取り込み対象 | 設定ファイル（実物用は公開しない側） |
| 索引の置き場所 | 索引フォルダのパス | 設定ファイル |
| 質問セットの場所 | 評価で使うファイルのパス | 設定ファイル |
| 埋め込みモデル名 | 選定手順で決まったモデル | 設定ファイル（選定後に記入） |

| 統合の定数 | 順位統合の定数。初期値60 | 設定ファイル（外出し） |
| 候補あり判定の閾値 | 総合結合で確定した値を記入する | 設定ファイル（確定後に記入） |
