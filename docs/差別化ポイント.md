# 差別化ポイント（このポートフォリオの売り）

「RAGを作りました」だけでは埋もれる。何が他と違うかを先に決め、
各工程で意図して入れていくための一覧（2026-11-26 本人方針）。
工程のたびに見直し、増えたら足し、弱いものは正直に弱いと書く。

## 入れている差別化

| 差別化 | 何が違うか | 証拠（リポジトリ内の場所） |
|---|---|---|
| 全工程を踏む進め方 | いきなりコードを書かず、要件定義からシステムテストまで成果物とゲートを残す | docs/ の設計文書一式、process/ の工程記録 |
| 手順の標準化 | 全工程にスキル（標準手順）とAgent（役割定義）を置き、進め方自体も設計してある | skills/、agents/、docs/00-1_スキルとAgentの設計.md |
| 自己レビューの仕組み | ゲート前に自己レビューを必須化。観点の資産化、判定への根拠必須、数えられる項目の機械確認、後工程で見つかった不具合を「レビュー漏れ」として数える | skills/common-self-review、process/reviews/ |
| 自己レビューの検出率の実測 | 欠陥を7件埋め込んだ設計書で、事情を知らないAgentにスキルだけ渡して自己レビューさせ、6件検出（約86%）。未検出の分析と、本物の指摘3件への対応まで記録した（対象は自己レビュースキル×設計文書の範囲。他スキルの再現性は未実測） | process/reviews/ドライラン評価の結果（自己レビュー）.md |
| 過程の公開 | 決定、差し戻し、振り返り、順番の間違いまで消さずに残す | process/decisions、process/phases |
| 評価の作法 | 方式を比べる評価（キーワードのみとの比較）、答えがない質問での誤判定も測る。実データは数字だけ、サンプルは再実行可能に | 評価結果の文書、サンプルの質問セット |
| 成果物の形式 | 要件定義書はWord、設計書はExcel、システム構成図とフロー図つき。日本の開発現場の実務形式に合わせる | docs/01_要件定義書.docx、docs/02_外部設計書.xlsx、docs/03_内部設計書.xlsx、docs/figures/ |
| 実データを見せずに証明する構成 | 実物と索引は公開せず、架空サンプルで再現可能にし、実データの集計値だけ出す二層構成 | docs/公開するものとしないもの.md |

## 今後検討する差別化（未実施、正直に未実施と書く）

- レビュー漏れの実績値： 後工程で見つかった漏れの件数を、工程記録から集計して出す
- 実利用の記録： 日常で実際に使った質問と、その答えの正しさの記録（公開できる範囲で）
- 他スキルのドライラン評価： 図の作成や文章の構成など、自己レビュー以外のスキルでも再現性を測る

## 運用

- 各工程の自己レビューでは、この一覧も観点に入れる（「この工程の成果物は、差別化のどれを強くするか」）
- 新しい差別化を思いついたら、作る前にこの一覧へ「検討中」として足す
