## 1. 背景と課題

### 1.1 課題
最初の対象である「運用知識」（エージェントの運用ルール文書と、カスタムスキルの手順書）を例に取る。

1. 運用ルールと手順書が複数フォルダに散らばり（運用ルール文書の置き場と、スキル32件のフォルダ群）、必要な記述を探すのに時間がかかる
2. キーワード検索では言い回しの違いで見つからない。意味で探せる必要がある一方、固有名詞や数字はキーワードの方が強い場面もある
3. AIエージェント（ネロ）は長期メモリと文脈に載っている範囲しか即答できず、文書の全文を対象にした正確な出典付きの回答ができない

将来の文書セット（生活文書など）でも同型の課題がある：文書が散らばり、言い回しの違いで見つからず、エージェントのメモリに入っていない中身には答えられない。

### 1.2 狙い
自分の文書を検索可能にし、普段使うAIエージェント（ネロ）からツールとして
呼び出せるようにする。出典付きで答えられる「第二の脳」の基盤を作り、
文書セットを差し替えれば生活文書などにも広げられる形にする。

## 2. 利用者

| 利用者 | 使い方 |
|---|---|
| 本人 | エージェント経由で運用ルールを確認する（「ブラウザ作業はどこでやる決まり？」等）。直接CLIで検索もする |
| AIエージェント（ネロ） | 質問に関連するチャンクを検索ツールで取得し、出典付きで回答を生成する |
| （ポートフォリオの読み手） | 要件→設計→評価結果の順で、課題設定と技術判断を確認する |

## 3. 機能要件

| 要件 | 内容 | 優先度 |
|---|---|---|
| 文書の取り込み | 指定フォルダの Markdown / テキスト / PDF を取り込めること（ingest） | 必須 |
| チャンク分割と出典の保持 | 文書を見出し・段落単位でチャンク分割し、出典（文書名・見出し・位置）を保持すること | 必須 |
| 出典付き検索 | 自然文の質問で検索し、関連チャンクを出典付きJSONで返せること（search） | 必須 |
| 答えがない場合の扱い | 文書に答えがない場合、その旨が分かる結果を返すこと（無関係なチャンクを根拠にしない） | 必須 |
| コマンドライン（CLI） | CLIから ingest / search / eval が実行できること | 必須 |
| MCPサーバー | MCPサーバーとして `search_knowledge` ツールを提供できること | あった方がよい（第2段階） |
| 評価の算出 | 評価セット（質問・期待する出典）で Recall@5 等を算出できること（eval） | 必須 |
| 差分取り込み | 文書の追加・更新時に差分だけ再取り込みできること | あった方がよい |
| askモード（単体での回答生成） | LLM APIを直接使う単体 `ask` モード（エージェントなしでも回答生成） | 任意 |

## 4. 非機能要件

| 要件 | 内容 |
|---|---|
| プライバシー | 文書全文とベクトルDBは、公開しない環境（ネロの作業環境、または本人のPC）だけに置く。公開リポジトリには実データを含めない。回答生成に使うのは検索で得た関連チャンクのみとする |
| ローカル動作 | ローカルで動くこと。ベクトルDBの常駐サーバーを前提にしない。埋め込みは原則ローカルモデルとし、外部APIを使う場合は設計書で理由と送信範囲を明記する |
| 日本語対応 | 日本語で検索できること。埋め込みモデルの選定は評価結果で決める（過去に意味検索でゲート未達だった経験があるため、実測なしに採用しない） |
| 性能 | ネロの作業環境で、文書数百件規模の取り込みと検索が実用的な時間で終わること（実測後に数値を確定）。文書セットを本人のPC側に広げる場合も、同等の性能を目安とする |
| 出典の正確さ | 出典の正確性：返却するチャンクの出典は実在の文書・見出しに対応すること |

## 5. 対象外

- 文書の自動編集・要約の保存（検索と回答の基盤に絞る）
- Web UI（CLI／MCPで成果を示せるため初版では対象外。必要なら後付け）
- Notion / Gmail 等の外部サービスの常時同期（初版はローカルフォルダ取り込みに絞る。連携は将来拡張）
- 他人との共有・マルチユーザー対応

## 6. 受け入れ基準（合格ゲート、先に定義する）

1. 最初の文書セット（本人が選んだ実文書、公開しない）を取り込み、エージェント（ネロ）経由で出典付き回答が返ることを実機で確認する
2. 評価セット30件以上で Recall@5 を測り、キーワード検索のベースラインと比較した結果を `docs/評価結果.md` に記録する
3. 答えがない質問（最低5件）で、根拠のない回答を作らないことを確認する
4. 公開リポジトリ側はサンプルドキュメントだけで第三者が再実行できる

## 7. 最初の文書セット（決定済み： 運用知識）

2026-11-26に本人が決定した（決定「最初の取り込み対象は運用知識にする」）。

- 運用ルールの文書（workspace/ops）： チェック観点リスト、エージェント権限ポリシー、ジョブのウォッチドッグ台帳、スケジュール構成マップ、システムファイルのメンテナンス方針
- カスタムスキル32件の手順書（workspace/custom-skills）
- 合計でMarkdown約68ファイル（2026-11-26時点の実数）

設計への波及（外部設計で正式決定する）：
- 文書の置き場所は本人のPCではなくネロの作業環境側。この文書セットでは「検索はネロの環境内、生成もネロ」という構成になる
- 運用知識の実物は公開しない。公開用は架空サンプルで代替し、実物は公開前チェックの対象にする

候補だった新居・生活文書と学習資料は、第2弾以降の文書セットとして残す（破棄ではない）。
