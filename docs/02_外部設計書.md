## 1. 要件との対応

| 要件（名前） | 対応する機能・インターフェース |
|---|---|
| 文書の取り込み | CLI `ingest`。対応形式は Markdown／テキスト／PDF。ただし初版の評価と受け入れ判定の対象は Markdown とテキストとし、PDFは取り込み可能であることまでを保証する（自己レビューでの指摘により明記。ゲートで本人の確認を取る） |
| チャンク分割と出典の保持 | 取り込み時の分割と、検索結果に含める出典情報（§5） |
| 出典付き検索 | CLI `search`、MCPツール `search_knowledge` |
| 答えがない場合の扱い | 検索結果の「答えの候補があるか」の明示（§5）。無関係な結果を根拠にしない |
| コマンドライン（CLI） | `ragcli` の3コマンド（§4） |
| MCPサーバー | 第2段階。CLIと同じ検索結果形式で提供する（§4.3） |
| 評価の算出 | CLI `eval` と評価結果の出力形式（§6） |
| 差分取り込み | `ingest` の再実行時の振る舞い（§4.1） |
| askモード（単体での回答生成） | 任意・後回し。初版のインターフェースには含めない |
| プライバシー | 配置と公開範囲（§3、§7）。詳細は `公開するものとしないもの.md` |
| ローカル動作 | 常駐サーバーなし。コマンド実行のたびに索引を開く形（§2） |
| 日本語対応 | 質問・文書とも日本語を前提とする。実現方法は内部設計 |
| 性能 | 文書数百件規模で実用的な応答。数値は実測後に受け入れ基準側へ反映 |
| 出典の正確さ | 出典は文書名と見出しで示し、実在確認をテスト工程で行う |

## 2. 全体構成

```text

実物の文書フォルダ（運用知識）
│ ragcli ingest
▼
索引（ベクトル索引＋キーワード索引、出典情報つき） ── 公開しない
▲
│ ragcli search ／ MCP search_knowledge
ネロ（質問を受け、検索し、出典付きで回答を生成する）


質問セット ── ragcli eval ──► 評価結果（サンプル分は公開、実データ分は集計値だけ公開）


コード一式、設計文書、スキルとAgent、過程の記録、
架空サンプル文書とその質問セット・評価結果、実データ評価の集計値
```

- 実行場所：最初の文書セット（運用知識）では、文書のあるネロの作業環境で実行する
- コードは環境に依存しない形で書き、将来は本人のPC側の文書セットにも同じ道具を使えるようにする
- 常駐プロセスは置かない。コマンドとMCPサーバー（起動時のみ）が索引を開いて使う

## 3. 配置と公開範囲

| 置くもの | 置き場所 | 公開 |
|---|---|---|
| 実物の文書 | ネロの作業環境（対象フォルダ） | しない |
| 索引 | ネロの作業環境（専用フォルダ、版管理から除外） | しない |
| 実データ用の質問セット | ネロの作業環境 | しない（件数と集計値だけ公開） |

| 実データ評価の集計値 | リポジトリ（評価結果の文書） | する |

## 4. インターフェース仕様

コマンド名は `ragcli` に統一する（叩き台で `rag` と書いていたものは本書で読み替える）。

### 設定ファイル
- ファイル名：`ragcli.toml`。書く項目は、対象の文書フォルダ（複数可）、索引の置き場所、質問セットの場所
- 公開リポジトリには架空サンプル用の設定を置く。実物用の設定は `ragcli.local.toml`（公開しない）で分け、そちらがあれば優先する
- 設定ファイルが無い、または中身が不正な場合は、使い方の誤りとして終了コード2で理由を表示する

### 4.1 取り込み： `ragcli ingest`
- 入力：対象フォルダ（設定ファイルに列挙する。複数可）
- 振る舞い：
- 対象の Markdown／テキスト／PDF を読み、分割して索引を作る
- 再実行時は、追加・更新された文書だけを差分で取り込む。前回から消えた文書は索引からも消す
- 読めなかったファイルは失敗で止めず、警告として一覧を出す
- 出力：取り込んだ文書数、分割数、警告の一覧をJSONで標準出力に出す（検索と同じく機械が読む形式を正とする）。異常終了時は理由を標準エラーに出す

### 4.2 検索： `ragcli search`
- 入力：質問文（引数）。任意で件数（既定5件）
- 出力：JSON（§5）を正とする。あわせて、本人が直接使うときのための簡易表示（文書名・見出し・一節の抜粋）も初版に含める
- 答えの候補がない場合も正常終了し、その旨をJSONで返す（§5）

### 4.3 MCPサーバー（第2段階）
- ツール名：`search_knowledge`。引数は質問文と件数。返却は `search` と同じJSON
- 通信方式は標準入出力（stdio）を前提とする。詳細は内部設計

### 4.4 終了コード
| コード | 意味 |
|---|---|
| 0 | 正常終了（検索で候補なし、も含む） |
| 2 | 使い方の誤り（引数不足など） |
| 3 | 索引がない（先に取り込みが必要） |
| 4 | 取り込み・評価の実行失敗 |

## 5. 検索結果の形式（JSON）

```json
{
"question": "ブラウザ作業はどこでやる決まりか",
"has_answer_candidate": true,
"hits": [
{
"document": "ブラウザ作業のルール（サンプル）",
"heading": "作業場所",
"text": "（該当する一節）",
"score": 0.82
}
]
}
```

- `has_answer_candidate` は、関連するチャンクがあり、その関連度が閾値以上のときに true とするのが外部仕様としての期待である。閾値の決め方は内部設計で定め、評価で調整する。答えがない質問で誤って true になった割合は、評価結果に含める
- `has_answer_candidate` が false のとき、 hits は空か、根拠に使えない参考情報であることを呼び出し側（ネロ）が区別できる形にする
- `score` は統合後の関連度を0〜1に正規化した値で、大きいほど関連が強い。算出方法は内部設計
- 出典は「文書名＋見出し」で示す。実物のファイルパスは検索結果に含めない（サンプルの相対パスは可）

## 6. 評価の入出力

- 入力：質問セット（質問文、期待する文書名と見出し、答えがない質問かの区分）
- 出力：質問ごとの結果と集計（Recall@5、出典の正確率、答えがない質問で候補なしと返せた割合）。方式（キーワードのみ／ベクトルのみ／組み合わせ）を切り替えて同じ形式で出せること
- 実データ用とサンプル用で形式は同じにし、公開する範囲だけを変える

## 7. プライバシーの境界

- 索引と実物文書は、公開しない環境の外に出ない
- 検索結果としてネロが受け取るのは、質問に関連する上位のチャンクだけ（文書全文は渡らない）
- 回答生成はネロ自身が行うため、生成のために文書を外部サービスへ送る経路は作らない
- 埋め込みに外部のAPIを使う構成を内部設計で選ぶ場合は、送信する範囲と理由を内部設計書に明記し、本人の確認を取ってから採用する（要件の「ローカル動作」と同じ制約）
- 公開前の確認は、共通スキルの「公開前チェック」（作成時期は未決）か、それまでは工程記録での目視確認で行う

## 8. 例外時の振る舞い（利用者から見える姿）

| 状況 | 振る舞い |
|---|---|
| 索引がまだない | 終了コード3と「先に取り込みが必要」のメッセージ |
| 索引の形式の版が合わない | 終了コード3と「再取り込みが必要」のメッセージ |
| 質問に答える文書がない | 正常終了し、`has_answer_candidate: false` を返す |
| 取り込みで読めないファイルがある | そのファイルだけ飛ばし、警告一覧に残す。他は取り込む |
| 対象フォルダが空／存在しない | 使い方の誤りとして終了コード2、理由を表示 |
| 評価セットの形式が違う | どの行がどう違うかを表示して終了コード4 |

## 9. サンプル文書セットの設計

- 種類と構造は実物の運用知識を模す：運用ルールの文書、スキルの手順書、台帳形式の表、スケジュールや方針のメモ
- 件数：15〜20件を目安とする（評価が意味を持つ規模。最終件数は製造時に確定し、工程記録に残す）
- 内容はすべて創作。人名・数値・ルールは実物から転用しない
- サンプル用の質問セットは30件以上（答えがない質問を最低5件）とし、期待する出典を付ける

## 10. 内部設計へ送る事項

- チャンクの切り方の具体（見出し単位と長さ上限の組み合わせ）
- 埋め込みモデルの選定手順と比較方法
- キーワード検索とベクトル検索の結果の統合方法
- 索引の実装方式（ファイルベースの候補から選定）と、差分検出の方法（更新日／内容のハッシュ等）
- `has_answer_candidate` の判定方法（スコアの閾値など）
- 評価の集計方法の具体と、方式切り替えの実装
- MCPサーバーの実装方式
