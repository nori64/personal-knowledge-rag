# personal-knowledge-rag

自分の文書をローカルで検索し、出典（文書名・見出し・位置）つきで取り出すための個人用ナレッジRAG。
検索は手元で完結し、回答の生成はAIエージェント側が行う。文書そのものを外部へ送らない設計。

> このリポジトリに置くのは、コード・設計文書・架空のサンプル文書だけです。
> 実際に使う文書と、そこから作った索引・質問セットは公開しません（[公開するものとしないもの](docs/公開するものとしないもの.md)）。

## 何ができるか

- **取り込み（ingest）**：Markdown／テキスト／PDFを、見出し単位でチャンクに分け、埋め込みを作って索引化する。ファイルのハッシュで差分管理し、変わった文書だけ作り直す
- **検索（search）**：キーワード検索（BM25＋Janome）、ベクトル検索（ローカルの埋め込みモデル）、両者の統合（RRF）から選べる。結果には出典と本文が付き、「答えの候補があるか」の判定も返す。候補がないとき、使う側は根拠のない回答を作らない
- **MCPサーバー**：同じ検索を `search_knowledge` ツールとして公開し、AIエージェントから呼べる
- **評価（eval）**：質問セット（期待する出典つき）で Recall@5、答えなし検出率などを測る

## 動かし方

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e .

# 架空サンプル（16文書）で試す
ragcli --config ragcli.toml ingest
ragcli --config ragcli.toml search "パスワードはどこで管理しますか"
ragcli --config ragcli.toml eval

# MCPサーバーとして起動（stdio）
ragcli-mcp --config ragcli.toml
```

- 初回の取り込みで埋め込みモデル（数百MB〜数GB）をダウンロードします
- 自分の文書で使う場合は、設定ファイルを分けて文書フォルダと索引の置き場所を指定します。その設定と索引は公開しない運用です

## 測った結果

サンプル文書（33問、再実行可能）と、実データ（26問、集計値のみ公開）で評価した。詳細は[評価結果](docs/08_評価結果.md)。

| 対象 | 方式 | 節レベル Recall@5 | 答えなし検出率 |
|---|---|---|---|
| サンプル（e5-small） | 統合 | 100% | 83.3% |
| 実データ（bge-m3、見出し込み埋め込み） | ベクトルのみ | 90.0% | 100% |

実データでの学び：

- 埋め込みモデルで大きく違う（同じ条件で e5系 35%／bge-m3 65%→改善後90%）
- 「キーワード＋ベクトルの統合が常に良い」は成り立たなかった（実データでは30%まで悪化。コーパスの言語構成に依存する）
- 埋め込みに文書名・見出しを付けると節の精度が上がる。ただし類似度の分布が変わるため、候補あり判定の閾値は測り直しが必要

## 作り方（このリポジトリのもう一つの中身）

要件定義→外部設計→内部設計→製造→単体テスト→結合テスト→システムテストの全工程を踏み、各工程に標準手順（スキル）と担当Agentの役割定義を置いて進めた。自己レビューを各ゲートの必須条件にし、意思決定と工程の記録も残している。

- [工程定義](docs/00_工程定義.md)：工程・成果物・ゲートの一覧
- [要件定義書](docs/01_要件定義書.docx)（Word）／[外部設計書](docs/02_外部設計書.xlsx)・[内部設計書](docs/03_内部設計書.xlsx)（Excel、構成図・フロー図つき）
- [過程の記録](process/README.md)：意思決定・工程記録・レビュー記録
- [差別化ポイント](docs/差別化ポイント.md)：普通のポートフォリオと何を変えたか、実装済みと検討中の切り分け

## 限界

- 実データの質問セットは26件と小さく、開発者が作ったもの。数字は目安
- 回答の生成は範囲外（検索まで）。生成した回答の正しさは評価していない
- 埋め込みはローカル実行のみ。大きなモデルは取り込みに時間がかかる
